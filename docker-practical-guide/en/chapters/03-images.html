Chapter 3: Images

The Image is the thing we build, move, and ship. In this chapter we open it from the inside: what it's made of, why it's built from layers, and where we pull it from and push it to.

Understanding layers will change how you write your Dockerfile later, and make your Images smaller and faster.

What is an Image, really?

An Image is a read-only template. It contains everything the app needs to run: a filesystem, libraries, a runtime, and settings. But it isn't a single opaque file — it's built from stacked layers.

Layers

Each step in building the Image adds a new layer on top of the previous one. Every layer is read-only and represents only the change that step made.

An example of stacked layers for a typical app Image:

  • Base layer: a small Linux distribution (base image).
  • On top of it: the runtime and libraries.
  • Top layer: your app's files.

When you run a container from the Image, Docker adds a thin writable layer on top of the read-only image layers. Every change while the container runs is written only there, without touching the Image.

✅ Why do layers matter?

Layers are stored once and shared across all the Images and containers that use them. If ten Images share the same base layer, it's stored on disk once. This is also what makes pull and builds faster: only the new layers are transferred.

Image name: Registry, Repository, and Tag

A full image name has three parts:

  • Registry: where images are stored (default docker.io, i.e. Docker Hub).
  • Repository: the image name itself (official images live under library/).
  • Tag: a specific version (default latest).

❗ Beware the latest tag

latest is not "always the newest" — it's just a default tag that may point at any version. Rely on an explicit tag like nginx:1.27 for reproducible results.

Registries and Docker Hub

A Registry is a store for images. The most famous is Docker Hub (public and default), and there are others like the GitHub Container Registry (ghcr.io) and private registries inside companies.

Real-world analogy

✅ Stacked transparent sheets

Picture layers as transparent plastic sheets, each with part of the image drawn on it. Stack them and you get the full image. To change a top layer you don't need to redraw the lower ones — you only replace the sheet that changed.

And if you know Git, layers are like commits: each records the change on top of what came before, and the Registry is like GitHub but for images.

Common mistakes

⚠️ Relying on latest

What latest points to may differ between machines or over time, giving unexpected results. Pin an explicit tag.

⚠️ Forgetting docker login before pushing

Trying to push without logging in, or without naming the image after your username, fails with a permissions (denied) error.

⚠️ Confusing Repository and Tag

nginx is a repository, and 1.27 is a tag inside it. One repository holds many tags/versions.

Best practices

📌 Pin explicit tags

Use postgres:16, not postgres:latest, for reproducibility.

🛡️ Prefer official and verified images

Lower security risk and better maintenance than unknown community images.

🪶 Start from a small base

A smaller base = fewer layers, faster pulls, and a smaller attack surface.

Summary

Key ideas

  • An Image is built from stacked read-only layers, and a container adds a writable layer on top.
  • Layers are stored once and shared, saving space and speeding up pulls and builds.
  • An image name = registry/repository:tag, defaulting to Docker Hub and latest.
  • A digest is an immutable reference, while a tag is mutable.

Important commands

  • docker pull / docker images / docker history
  • docker tag / docker login / docker push

Mistakes to avoid

  • Relying on latest.
  • Forgetting to log in or to name the image after yourself before pushing.
