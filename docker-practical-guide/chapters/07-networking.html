الفصل 7: الشبكات (Networking)

نادرًا ما تعمل حاوية بمفردها. التطبيق يحتاج التحدّث إلى قاعدة بيانات، والعالم الخارجي يحتاج الوصول إلى التطبيق. هذا الفصل يشرح كيف تتواصل الحاويات: مع بعضها عبر الشبكة، ومع الخارج عبر ربط المنافذ.

أهم فكرة هنا — وكثيرًا ما تُغفَل — أن الحاويات على شبكة معرّفة تجد بعضها بالاسم تلقائيًّا. هذا ما سيربط تطبيقنا بقاعدته لاحقًا.

⏱️ زمن القراءة: — 📊 المستوى: متوسّط 🧪 معمل تطبيقي واحد

أهداف التعلّم

بنهاية هذا الفصل ستعرف كيف:

  • تفرّق بين الشبكة الافتراضية (default bridge) والمعرّفة (user-defined bridge).
  • تجعل الحاويات تتواصل بالاسم عبر DNS الداخلي.
  • تربط منفذ الحاوية بالمضيف عبر -p، وتعرف الفرق عن EXPOSE.
  • تتعرّف على شبكة host ومتى تُستخدم.
  • تدير الشبكات: الإنشاء والربط والفحص.

المتطلبات المسبقة

  • إنهاء الفصل 4 (تشغيل الحاويات) والفصل 6 (Volumes).
  • ربط المنافذ بـ -p (مرّ بنا في الفصل 2).

أنواع الشبكات (Network Drivers)

يوفّر Docker عدة «محرّكات» شبكة، أهمّها ثلاثة:

النوعالوصف
bridgeالافتراضي؛ شبكة خاصة معزولة على المضيف (الأكثر استخدامًا)
hostتشارك network stack الخاص بالمضيف مباشرةً دون عزل (Linux)
noneبلا شبكة إطلاقًا (عزل كامل)

الشبكة الافتراضية مقابل المعرّفة

كل حاوية تنضمّ افتراضيًّا إلى شبكة bridge افتراضية. لكن لها قيد مهم: الحاويات فيها لا تتعارف بالاسم، بل بعناوين IP فقط — وهي متغيّرة وغير عملية.

❗ القاعدة الذهبية

أنشئ دائمًا شبكة معرّفة (user-defined bridge) لتطبيقك. عليها فقط يعمل DNS الداخلي، فتصل كل حاوية إلى الأخرى باسمها كأنه اسم مضيف (hostname). هذا ما يجعل تطبيقك يصل إلى القاعدة عبر db بدل رقم IP.

ربط المنافذ (Port Mapping)

الشبكة تربط الحاويات ببعضها، لكن للوصول من خارج Docker (مثل متصفّحك) نحتاج نشر منفذ بـ -p:

تذكّر الفرق من فصل Dockerfile: EXPOSE توثيق فقط، بينما -p هو ما ينشر المنفذ فعليًّا للمضيف.

شبكة host و none

شبكة host تجعل الحاوية تشارك شبكة المضيف مباشرةً (لا حاجة لـ -p)، لكنها بلا عزل وتعمل بكامل مزاياها على Linux فقط. أما none فتعزل الحاوية تمامًا عن أي شبكة.

تشبيه من الواقع

✅ مقسّم هاتف داخلي

الشبكة المعرّفة كـمقسّم هاتف داخلي في شركة: كل موظّف (حاوية) له اسم، وينادي زملاءه بأسمائهم عبر دليل داخلي (DNS). أما ربط المنفذ (-p) فكـموظّف الاستقبال الذي يحوّل مكالمة من الخارج إلى رقم داخلي محدّد.

أخطاء شائعة

⚠️ توقّع التعارف بالاسم على الشبكة الافتراضية

DNS الداخلي يعمل على الشبكة المعرّفة فقط. أنشئ شبكة بـ docker network create واربط بها الحاويات.

⚠️ عكس ترتيب -p

الصيغة host:container. كتابة -p 80:8080 بدل -p 8080:80 توجّه الطلب لمنفذ خاطئ.

⚠️ نسيان وضع الحاويات على نفس الشبكة

حاويتان على شبكتين مختلفتين لا تريان بعضهما. يجب أن تتشاركا نفس الشبكة للتواصل.

⚠️ نشر منفذ القاعدة دون داعٍ

إن كان التطبيق وحده يحتاج القاعدة، فلا داعي لنشر 5432 للمضيف؛ يكفي أن تكون القاعدة على نفس الشبكة.

أفضل الممارسات

🔗 شبكة معرّفة لكل تطبيق

اجمع حاويات التطبيق الواحد على شبكة خاصة به لعزلها وتفعيل DNS.

🏷️ اتصل بالاسم لا بالـ IP

عناوين IP متغيّرة؛ أسماء الحاويات ثابتة وواضحة.

🔒 انشر أقل المنافذ

انشر فقط ما يحتاجه العالم الخارجي، وأبقِ الباقي داخليًّا.

ورقة الأوامر (Cheat Sheet)

الأمرالوظيفة
docker network create <name>إنشاء شبكة معرّفة
docker network lsعرض الشبكات
docker network inspect <name>تفاصيل الشبكة وحاوياتها
docker run --network <name> ...تشغيل حاوية على شبكة
docker network connect <net> <container>ربط حاوية عاملة بشبكة
docker run -p 8080:80 ...نشر منفذ للمضيف
docker network rm <name>حذف شبكة

الخلاصة

أهم الأفكار

  • أنشئ شبكة معرّفة (user-defined bridge) لأي تطبيق متعدّد الحاويات.
  • على الشبكة المعرّفة تتعارف الحاويات بالاسم عبر DNS الداخلي.
  • -p host:container ينشر المنفذ للخارج؛ وEXPOSE توثيق فقط.
  • localhost داخل الحاوية يعني الحاوية نفسها، لا حاوية أخرى.

أوامر مهمة

  • docker network create / ls / inspect / connect
  • --network <name> و -p host:container

أخطاء تجنّبها

  • الاعتماد على الشبكة الافتراضية للتعارف بالاسم.
  • استخدام localhost بين الحاويات.
