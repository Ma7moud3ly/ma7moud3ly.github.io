What is Docker Compose?

A tool that describes a multi-container app in a compose.yaml file, then manages it with one command. Instead of several docker run commands, everything is in one clear file you can keep in Git.

The structure of compose.yaml

The file is split into simple sections:

  • services: each container service (like app and db).
  • volumes: the persistent Named Volumes.
  • networks: networks (optional — Compose creates one automatically).

Inside each service we set image or build, ports, environment, volumes, and dependencies on other services.

✅ Automatic network and DNS by name

Compose creates a user-defined network for your app automatically and puts all the services on it. So each service reaches another by name directly — app reaches the database via db, exactly as we learned in the networking chapter.

Environment variables and the .env file

We pass settings via environment inside the service. To keep values out of the file, we put them in a .env file, and Compose reads it automatically.

Start order: depends_on

depends_on declares that a service starts before another (e.g. the database before the app).

⚠️ Started ≠ ready

depends_on guarantees the database started, not that it's ready to accept connections. The real "wait" solution is a health check — we'll see it in the next chapter.

Real-world analogy

✅ The orchestra conductor

Instead of each instrument (container) playing alone while you coordinate them by hand, the conductor reads one score (compose.yaml) so all the instruments start together and in harmony at a single cue.

Hands-on lab

🧪 Lab 8: turn the long commands into Compose

In Chapter 7's lab we ran the app and the database with two long commands. Let's replace them with one file.

  1. In the project folder, create compose.yaml as in the example above.
  2. Start the stack: docker compose up -d.
  3. Confirm both services: docker compose ps.
  4. Open http://localhost:8080 and try the app.
  5. Stop the stack: docker compose down, then run up -d again and note the data persists (the volume).

Common mistakes

⚠️ Wrong YAML indentation

YAML is whitespace-sensitive. Use spaces, not tabs, and align the sections precisely.

⚠️ Forgetting the database's volume

Without volumes on the database, its data is lost on down. Always mount a volume for database data.

⚠️ Relying on depends_on for readiness

It controls start order only, not readiness. To wait for real readiness, use a health check (next chapter).

⚠️ Using the old docker-compose

The modern command is docker compose (with a space). The hyphenated docker-compose is old.

Best practices

🗂️ One service per concern

Separate the app from the database from the cache — each its own service.

🔑 Settings in .env

Keep values and secrets out of compose.yaml and out of Git.

📌 Pin image versions

postgres:16, not postgres:latest.

💾 A volume for every persistent data

Databases and uploaded files → a Named Volume.

Cheat sheet

CommandWhat it does
docker compose up -dStart the stack in the background
docker compose psList services and their state
docker compose logs -f <service>Follow a service's logs
docker compose downStop and remove containers and network
docker compose down -vRemove volumes too
docker compose buildBuild the images defined with build
docker compose exec <service> shOpen a shell in a running service

Summary

Key ideas

  • Compose describes a multi-container app in one file and runs it with one command.
  • It creates a network automatically, so services recognize each other by name.
  • depends_on controls start order, not readiness.
  • Named Volumes survive down (except with -v).

Important commands

  • docker compose up -d / ps / logs
  • docker compose down / down -v

Mistakes to avoid

  • Wrong YAML indentation.
  • Expecting depends_on to wait for readiness.
