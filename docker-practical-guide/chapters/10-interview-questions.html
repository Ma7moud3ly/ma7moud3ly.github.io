1. أساسيات Docker والحاويات

🎤ما مشكلة «works on my machine» وكيف يحلّها Docker؟
عرض الإجابة

تنشأ من اختلاف بيئة التشغيل بين الأجهزة (إصدار runtime، إعدادات، dependencies). يحزم Docker التطبيق مع بيئته كاملة في Image واحدة تعمل بنفس الطريقة في كل مكان، فيلغي هذا الاختلاف.

🎤ما الفرق بين Virtual Machine و Container؟
عرض الإجابة

الـ VM يحاكي جهازًا كاملًا بنظام تشغيل ضيف فوق Hypervisor، فهو ثقيل (جيجابايتات) وبطيء الإقلاع. الـ Container عملية معزولة تتشارك نواة (kernel) المضيف، فهو خفيف (ميجابايتات) وسريع (ثوانٍ) وأعلى كثافة.

🎤ما الفرق بين Image و Container؟
عرض الإجابة

الـ Image قالب ثابت للقراءة فقط يحوي التطبيق وبيئته. الـ Container نسخة حيّة قابلة للتشغيل منه. من Image واحدة نشغّل عدة Containers (مثل Class و Object).

🎤هل تحتوي الحاوية على نظام تشغيل كامل؟
عرض الإجابة

لا. تحوي ملفات التطبيق وبيئته فقط، وتتشارك نواة نظام التشغيل المضيف. لهذا هي أخف وأسرع من الـ VM.

🎤اشرح معمارية Docker.
عرض الإجابة

ثلاثة مكوّنات: Docker Client (الأوامر التي تكتبها)، Docker Daemon (الخادم الذي يبني ويشغّل)، وRegistry (مخزن الـ Images مثل Docker Hub). يعمل بنموذج Client/Server عبر REST API.

🎤ما دور Docker Daemon؟
عرض الإجابة

العملية الخلفية (dockerd) التي تستقبل طلبات الـ Client وتنفّذها فعليًّا: بناء الـ Images وسحبها وتشغيل الحاويات وإدارتها.

🎤اذكر مراحل دورة حياة الحاوية.
عرض الإجابة

Created (docker create) ← Running (start) ← قد تمرّ بـ Paused ← Stopped (stop) ← Removed (rm). وdocker run يجمع الإنشاء والتشغيل.

🎤على Windows، أين تعمل الحاويات فعليًّا؟
عرض الإجابة

الـ CLI (docker.exe) يعمل أصلًا على Windows، لكن الـ Engine والحاويات تعمل داخل WSL 2 لأن الحاويات تحتاج نواة Linux. الـ Client يرسل الأوامر عبر API إلى الـ Daemon في WSL 2.

🎤هل يُلغي Docker الحاجة إلى بيئة التشغيل (runtime)؟
عرض الإجابة

لا. Docker لا يستبدل الـ runtime بل يحزمه. تطبيق Java مثلًا ما زال يحتاج JRE، لكنه الآن داخل الـ Image بإصدار محدّد نتحكّم به.

2. الـ Images والطبقات والسجلات

🎤مِمَّ يتكوّن الـ Image؟
عرض الإجابة

من طبقات (layers) ثابتة مكدّسة، كل طبقة تمثّل تغييرًا فوق ما قبلها، بالإضافة إلى metadata تصف كيفية تشغيله.

🎤ما فائدة تقسيم الـ Image إلى layers؟
عرض الإجابة

المشاركة والـ caching: الطبقات المشتركة تُخزَّن مرة واحدة، وعند البناء أو السحب تُعالَج الطبقات الجديدة فقط — توفير للمساحة والوقت.

🎤أين تُكتب تغييرات حاوية عاملة؟ وماذا يحدث لها عند الحذف؟
عرض الإجابة

في طبقة كتابة رقيقة (writable layer) فوق طبقات الـ Image الثابتة (copy-on-write). تختفي هذه الطبقة بحذف الحاوية، لذلك نستخدم volume للبيانات الدائمة.

🎤اشرح اسم الـ Image docker.io/library/nginx:1.27.
عرض الإجابة

docker.io = الـ Registry، library/nginx = الـ Repository (وlibrary/ للصور الرسمية)، و1.27 = الـ Tag.

🎤ما الفرق بين tag و digest؟
عرض الإجابة

الـ tag اسم قابل للتغيير قد يُعاد توجيهه لمحتوى آخر. الـ digest بصمة sha256 للمحتوى، ثابتة لا تتغيّر، فتضمن سحب نفس المحتوى بالضبط دائمًا.

🎤لماذا يُنصح بتجنّب latest؟
عرض الإجابة

لأنه وسم افتراضي قد يشير إلى إصدار مختلف بين الأجهزة أو مع الوقت، فتفقد قابلية التكرار (reproducibility). ثبّت وسمًا صريحًا.

🎤هل ينسخ docker tag الـ Image؟
عرض الإجابة

لا. يضيف اسمًا (مرجعًا) جديدًا يشير إلى نفس الطبقات. حذف أحد الأسماء لا يحذف الطبقات ما دام اسم آخر يشير إليها.

🎤ما شرط دفع Image إلى Docker Hub؟
عرض الإجابة

docker login، وأن يبدأ اسم الـ Image باسم المستخدم/المنظمة (username/repo:tag)، ثم docker push.

🎤كيف تقلّل حجم الـ Image؟
عرض الإجابة

base صغيرة (jre لا jdk)، multi-stage build، ترتيب التعليمات للـ caching، .dockerignore، ودمج أوامر RUN وإزالة الملفات المؤقّتة.

3. تشغيل الحاويات وإدارتها

🎤ما الفرق بين docker run و docker start؟
عرض الإجابة

run ينشئ حاوية جديدة من Image ويشغّلها. start يعيد تشغيل حاوية موجودة متوقّفة دون إنشاء جديدة.

🎤ماذا يعني -d و -it؟
عرض الإجابة

-d (detached): تشغيل في الخلفية. -it = -i (إبقاء المدخل مفتوحًا) + -t (طرفية TTY)، لجلسة تفاعلية مثل shell.

🎤ما الفرق بين docker stop و docker kill؟
عرض الإجابة

stop يرسل SIGTERM ويمهل العملية للإغلاق النظيف ثم SIGKILL. kill يرسل SIGKILL فورًا دون مهلة.

🎤ما الفرق بين exec و attach؟
عرض الإجابة

exec يشغّل عملية جديدة (مثل shell) داخل حاوية عاملة. attach يصلك بالعملية الرئيسية (PID 1)، وإغلاقها قد يوقف الحاوية.

🎤لماذا تتوقّف الحاوية فور تشغيلها أحيانًا؟
عرض الإجابة

لأن الحاوية تعيش ما دامت عمليتها الرئيسية (PID 1) حيّة. إن انتهت العملية (لا خدمة طويلة الأمد) توقّفت الحاوية. راجع السبب بـ docker logs.

🎤ما سياسات إعادة التشغيل (restart policies)؟
عرض الإجابة

no (افتراضي)، on-failure عند الأخطاء، always دائمًا، unless-stopped إلا إذا أوقفتها يدويًّا — مفيدة بعد إعادة إقلاع الجهاز.

🎤كيف تحذف كل الحاويات المتوقّفة؟
عرض الإجابة

docker container prune. ولحذف حاوية عاملة بالقوة: docker rm -f <name>.

4. Dockerfile

🎤ما الفرق بين COPY و ADD؟
عرض الإجابة

كلاهما ينسخ ملفات. ADD يفكّ أرشيفات tar تلقائيًّا وينزّل من رابط. نفضّل COPY لوضوحه، وADD عند الحاجة الصريحة فقط.

🎤ما الفرق بين CMD و ENTRYPOINT؟
عرض الإجابة

ENTRYPOINT البرنامج الثابت الذي يعمل دائمًا. CMD وسائط افتراضية قابلة للتغيير عند التشغيل. يُدمجان غالبًا: entrypoint للبرنامج و cmd للوسائط.

🎤ما الفرق بين RUN و CMD؟
عرض الإجابة

RUN يُنفَّذ وقت البناء ويصنع طبقة (مثل تثبيت أداة). CMD يحدّد ما يُنفَّذ وقت تشغيل الحاوية.

🎤لماذا نفضّل exec form على shell form؟
عرض الإجابة

صيغة الأقواس (exec form) تشغّل البرنامج مباشرةً كـ PID 1، فتصله إشارة SIGTERM ويتوقّف بشكل نظيف. صيغة النصّ (shell form) تمرّ عبر shell وتكسر تسليم الإشارة فيبطؤ الإيقاف.

🎤ما «build context» وما دور .dockerignore؟
عرض الإجابة

الملفات في المسار الممرّر لـ docker build والتي تُرسَل إلى الـ Daemon. .dockerignore يستبعد ما لا يلزم (مثل .git) فيصغُر السياق ويسرع البناء.

🎤لماذا يؤثّر ترتيب التعليمات على caching؟
عرض الإجابة

تغيير تعليمة يُبطل طبقتها وكل ما بعدها. وضع النادر التغيّر أولًا (مثل dependencies) والكود المتغيّر أخيرًا يعيد استخدام أكبر عدد من الطبقات.

🎤هل ينشر EXPOSE المنفذ؟
عرض الإجابة

لا، هو توثيق فقط. النشر الفعلي للمضيف يتم بـ -p host:container وقت التشغيل.

🎤ما multi-stage build ولماذا نستخدمه؟
عرض الإجابة

بناء على عدة مراحل: مرحلة تبني الـ artifact بأدوات البناء، ومرحلة تشغيل تأخذ الـ artifact فقط. النتيجة Image أصغر وأأمن دون أدوات بناء ولا كود مصدري. ينسخ COPY --from=build من مرحلة سابقة.

🎤لماذا نشغّل الحاوية بمستخدم non-root؟
عرض الإجابة

لتقليل أثر أي اختراق. نُنشئ مستخدمًا محدود الصلاحيات ونشغّل به عبر USER، فلا يحصل المهاجم على صلاحيات واسعة داخل الحاوية أو المضيف.

5. التخزين (Volumes)

🎤لماذا تكون بيانات الحاوية سريعة الزوال؟
عرض الإجابة

لأنها تُكتب في طبقة الكتابة الخاصة بالحاوية، وتُحذف بحذفها. للاحتفاظ بها نخزّنها في volume مستقل عن دورة حياة الحاوية.

🎤ما الفرق بين Named Volume و Bind Mount؟
عرض الإجابة

الـ Named Volume يديره Docker في منطقته الداخلية، الأنسب للبيانات الدائمة والقابلة للنقل. الـ Bind Mount يربط مسارًا من المضيف، الأنسب للتطوير حيث تنعكس التغييرات فورًا.

🎤كيف تحفظ بيانات PostgreSQL بثبات؟
عرض الإجابة

بربط Named Volume بمجلد بياناتها: -v tasks-db:/var/lib/postgresql/data، فتبقى بعد حذف الحاوية.

🎤هل يحذف docker rm الـ volume المرتبط؟
عرض الإجابة

لا. الـ Named Volume يبقى (حمايةً للبيانات). يُحذف صراحةً بـ docker volume rm، أو docker volume prune لغير المستخدم.

🎤ما الـ anonymous volume ولماذا ننتبه له؟
عرض الإجابة

volume بلا اسم يُنشئه Docker تلقائيًّا (غالبًا عبر تعليمة VOLUME). يصعب تتبّعه ويتراكم، لذا نفضّل تسمية الـ volumes وننظّف غير المستخدم بـ prune.

6. الشبكات (Networking)

🎤ما الفرق بين default bridge و user-defined bridge؟
عرض الإجابة

على الشبكة المعرّفة يعمل DNS الداخلي فتتعارف الحاويات بالاسم؛ على الافتراضية تتصل بعناوين IP فقط. لذا ننشئ شبكة معرّفة لأي تطبيق متعدّد الحاويات.

🎤كيف تجد الحاويات بعضها؟
عرض الإجابة

عبر DNS الداخلي على شبكة معرّفة مشتركة: يصبح اسم الحاوية hostname يمكن للأخرى الاتصال به مباشرةً.

🎤ماذا يفعل -p 8080:80 وما الفرق عن EXPOSE؟
عرض الإجابة

ينشر منفذ الحاوية 80 على منفذ المضيف 8080 (الصيغة host:container)، فيصبح الوصول من خارج Docker متاحًا. EXPOSE توثيق فقط ولا ينشر شيئًا.

🎤لماذا لا نستخدم localhost بين حاويتين؟
عرض الإجابة

لأن localhost داخل الحاوية يشير إلى الحاوية نفسها، لا إلى حاوية أخرى أو المضيف. نستخدم اسم الحاوية الهدف على الشبكة المشتركة.

🎤ما شبكة host ومتى تُستخدم؟
عرض الإجابة

تجعل الحاوية تشارك network stack الخاص بالمضيف مباشرةً دون عزل ولا حاجة لـ -p. مفيدة للأداء على Linux، لكنها تفقد العزل وتعمل بكامل مزاياها على Linux فقط.

🎤هل تتواصل حاويتان على شبكتين مختلفتين؟
عرض الإجابة

لا، إلا إذا وُصلت إحداهما بالشبكة الأخرى (docker network connect) أو شاركتا شبكة واحدة.

7. Docker Compose

🎤ما هو Docker Compose ومتى تستخدمه؟
عرض الإجابة

أداة لوصف وتشغيل تطبيق متعدّد الحاويات من ملف compose.yaml واحد. تستخدمه حين يتكوّن التطبيق من عدة خدمات (تطبيق + قاعدة + كاش…) تُدار معًا.

🎤ما أقسام compose.yaml الأساسية؟
عرض الإجابة

services (الحاويات)، volumes (التخزين الدائم)، وnetworks (اختياري لأن Compose ينشئ واحدة تلقائيًّا).

🎤كيف تجد الخدمات بعضها في Compose؟
عرض الإجابة

يضع Compose كل الخدمات على شبكة معرّفة واحدة، فتصل كل خدمة إلى الأخرى باسم الخدمة كـ hostname عبر DNS الداخلي.

🎤ما الفرق بين down و stop؟
عرض الإجابة

stop يوقف الحاويات فقط. down يوقفها ويحذفها مع الشبكة. الـ Named Volumes تبقى إلا مع down -v.

🎤ماذا يضمن depends_on؟
عرض الإجابة

ترتيب البدء فقط، لا الجاهزية لقبول الاتصالات. للجاهزية نستخدم health check مع condition: service_healthy.

🎤كيف تمرّر الإعدادات والأسرار دون كتابتها في الملف؟
عرض الإجابة

عبر ملف .env بجانب compose.yaml ثم ${VAR} داخل الملف. للإنتاج تُستخدم أدوات أسرار مخصّصة، ولا تُرفع القيم إلى Git.

🎤ما الفرق بين image و build في الخدمة؟
عرض الإجابة

image يستخدم Image جاهزة من سجل. build يبني الـ Image من Dockerfile محلي وقت التشغيل.

8. التطبيقات الحقيقية والإنتاج

🎤كيف تضبط اتصال تطبيق بقاعدة داخل حاوية؟
عرض الإجابة

عبر متغيّرات البيئة (مبدأ 12-factor) بدل كتابة الإعدادات في الكود، فيمكن تغييرها لكل بيئة دون إعادة بناء الـ Image.

🎤ما الذي نضعه مكان المضيف في رابط اتصال القاعدة؟
عرض الإجابة

اسم خدمة القاعدة على الشبكة (مثل db)، لأن الخدمات تتعارف بالاسم. ليس localhost.

🎤كيف تنتظر جاهزية القاعدة قبل بدء التطبيق؟
عرض الإجابة

depends_on وحده يضمن البدء لا الجاهزية. نضيف health check للقاعدة (pg_isready) ونجعل التطبيق ينتظر condition: service_healthy. ويُستحسن أن يعيد التطبيق المحاولة عند فشل الاتصال.

🎤كيف تفحص صحّة التطبيق داخل الحاوية؟
عرض الإجابة

عبر نقطة health يوفّرها التطبيق (في Spring Boot: Actuator و/actuator/health) نستعملها في HEALTHCHECK أو المنسّق (orchestrator).

🎤أين تضع الأسرار في الإنتاج؟
عرض الإجابة

خارج الـ Image دائمًا: متغيّرات بيئة أو أداة إدارة أسرار، تُمرّر وقت التشغيل. لا تُبنى داخل الطبقات (يمكن استخراجها) ولا تُرفع إلى سجل عام.

🎤لماذا نراعي ذاكرة الـ JVM داخل الحاوية؟
عرض الإجابة

يجب أن يحترم الـ JVM حدود ذاكرة الحاوية لا ذاكرة المضيف. نضبط -XX:MaxRAMPercentage لتفادي تجاوز الذاكرة وقتل الحاوية (OOM Killed).

🎤كيف تفحص Image بحثًا عن ثغرات؟
عرض الإجابة

بأدوات مثل docker scout أو Trivy، تفحص الطبقات والحزم مقابل قواعد بيانات الثغرات المعروفة، وتُدمج غالبًا في خط الـ CI.

🎤ما دور CI/CD مع Docker؟
عرض الإجابة

أتمتة بناء الـ Image وفحصها ودفعها إلى سجل عند كل تغيير، ثم نشرها. فتصبح الإصدارات متّسقة وقابلة للتكرار وسريعة، دون خطوات يدوية.

🎤كيف تجعل بناء الـ Image قابلًا للتكرار (reproducible)؟
عرض الإجابة

ثبّت وسوم الأساس (وربما digest)، ابنِ داخل Docker عبر multi-stage (لا تعتمد على جهازك)، استخدم .dockerignore، وثبّت إصدارات الـ dependencies.

نصائح سريعة للمقابلة

  • اربط كل إجابة بمثال عملي فعلته (بناء Image، volume، شبكة، Compose).
  • عندما تُسأل «لماذا»، اذكر البديل وعيوبه، لا التعريف فقط.
  • كن صريحًا فيما لا تعرفه، ثم اشرح كيف ستبحث عنه.
  • راجع الفروق الشائعة: Image/Container، CMD/ENTRYPOINT، volume/bind mount، bridge الافتراضية/المعرّفة.
