Chapter 5: Dockerfile

So far we've run ready-made Images. Now we build our own Image.

A Dockerfile is a text file with the steps to build the Image. Docker runs these steps one after another, and each step makes a layer. We'll apply this to a simple Java app.

⏱️ Reading time: — 📊 Level: Intermediate 🧪 1 hands-on lab

Learning objectives

By the end of this chapter you'll know how to:

  • Understand the role of each Dockerfile instruction.
  • Build an Image with docker build.
  • Tell CMD from ENTRYPOINT, and COPY from ADD.
  • Order instructions to speed up builds (layer caching).
  • Shrink the build with a .dockerignore file.

Prerequisites

  • Finishing Chapter 3 (Images and layers) and Chapter 4 (running containers).

The core instructions

These are the most-used instructions. Each does something simple and clear:

InstructionWhat it does
FROMChoose the base image
WORKDIRSet the working directory inside the Image
COPYCopy files from your machine into the Image
ADDLike COPY but with extra behavior (unpack, download a URL)
RUNRun a command at build time
ENVDefine an environment variable
EXPOSEDocument the port the app listens on
CMDThe default command at run time (overridable)
ENTRYPOINTThe fixed command that always runs

COPY or ADD?

Both copy files. The difference is that ADD does extra things: it unpacks tar files and downloads from a URL. That extra behavior causes surprises.

✅ The rule

Always use COPY. Only reach for ADD when you clearly need it.

CMD or ENTRYPOINT?

Both define what runs when the container starts, but there's a small difference:

  • ENTRYPOINT: the fixed program that always runs, like java -jar app.jar.
  • CMD: default arguments the user can change at docker run.

Always write them in bracket form (exec form). This form runs the program directly:

❗ Avoid the shell form

Writing ENTRYPOINT java -jar app.jar runs the program through a shell. Then your program isn't PID 1, the stop signal doesn't reach it properly, and stopping the container becomes slow. Stick to bracket form.

Build context and the .dockerignore file

On docker build, Docker sends the whole folder's contents to it (the build context). A .dockerignore file excludes what you don't need (like .git), making the build faster and the Image cleaner.

Real-world analogy

✅ A cooking recipe

A Dockerfile is a recipe. FROM is the base ingredient, COPY and RUN are the prep steps, and ENTRYPOINT is how it's served. The same recipe yields the same dish in any kitchen.

Instruction order and caching

Docker caches the result of each layer. If an instruction hasn't changed, it reuses the layer instead of rebuilding it. So order your instructions: things that rarely change first, and code that changes often last.

Common mistakes

⚠️ An order that breaks the cache

Copying the code before the dependencies re-downloads them on every small change. Put what rarely changes first.

⚠️ Using ADD needlessly

Its extra behavior can surprise you. The default is always COPY.

⚠️ Thinking EXPOSE publishes the port

EXPOSE is documentation only. Publishing to the host is done with -p at run time.

⚠️ A heavy base image

Using jdk instead of jre at run time bloats the Image for nothing. Use only the runtime you need.

Best practices

🧱 Order for caching

Rarely-changing things first, changing code last, so rebuilds are faster.

🚫 Always a .dockerignore

Excludes .git and unneeded files, shrinking the build and the Image.

📎 Bracket form

Use ["...", "..."] for correct signal handling and a clean stop.

📌 Pin the base tag

eclipse-temurin:21-jre, not :latest.

Summary

Key ideas

  • A Dockerfile is a file of steps; each instruction makes a layer.
  • Use COPY, and ENTRYPOINT in bracket form.
  • Order instructions to benefit from caching, and exclude the extra with .dockerignore.
  • EXPOSE is documentation only; publishing is done with -p.

Important items

  • FROM / WORKDIR / COPY / ENTRYPOINT
  • docker build -t name:tag .

Mistakes to avoid

  • An order that breaks the cache.
  • Shell form in ENTRYPOINT, and a heavy base image.
