الفصل 9: Spring Boot مع PostgreSQL

الآن نجمع كل ما تعلّمناه على تطبيق حقيقي: خدمة Spring Boot مع قاعدة PostgreSQL، داخل حاويات، ببيانات دائمة، وبانتظار صحيح لجاهزية القاعدة.

هنا يظهر لماذا كل فصل سابق كان مهمًّا: Image للتطبيق، volume للبيانات، شبكة للتواصل بالاسم، و Compose ليجمعها.

⏱️ زمن القراءة: — 📊 المستوى: متقدّم 🧪 معمل تطبيقي واحد

أهداف التعلّم

بنهاية هذا الفصل ستعرف كيف:

  • تبني Image لتطبيق Spring Boot.
  • تربط Spring Boot بـ PostgreSQL عبر متغيّرات البيئة.
  • تكتب compose.yaml للتطبيق والقاعدة مع volume دائم.
  • تضيف health check وتنتظر جاهزية القاعدة قبل بدء التطبيق.
  • تستخدم Spring profile خاصًّا بالحاويات.

المتطلبات المسبقة

  • إنهاء الفصل 5 (Dockerfile) والفصل 8 (Compose).
  • تطبيق Spring Boot يستخدم PostgreSQL (أو خدمة المهام من هذا الدليل).

حاويّة تطبيق Spring Boot

يبني Spring Boot ملف jar واحدًا يحوي كل شيء (fat jar). حاويّته إذًا بسيطة: Image فيها JRE، ننسخ الـ jar، ونشغّله. لا فرق جوهري عن أي تطبيق Java.

ربط Spring بالقاعدة عبر البيئة

لا نكتب رابط القاعدة داخل الكود. يقرأ Spring Boot الإعدادات من متغيّرات البيئة، فنمرّرها للحاوية:

  • SPRING_DATASOURCE_URL — رابط JDBC للقاعدة.
  • SPRING_DATASOURCE_USERNAME — اسم المستخدم.
  • SPRING_DATASOURCE_PASSWORD — كلمة المرور.

✅ الوصول بالاسم

في رابط القاعدة نستخدم اسم الخدمة كـ hostname: jdbc:postgresql://db:5432/tasks. الكلمة db هي اسم خدمة القاعدة في Compose، لا localhost.

Health check وانتظار الجاهزية

رأينا أن depends_on يضمن أن القاعدة بدأت، لا أنها جاهزة. الحل هو health check للقاعدة، ثم جعل التطبيق ينتظر حتى تصبح «صحّية»:

  • القاعدة: أمر فحص pg_isready يتكرّر حتى تنجح.
  • التطبيق: depends_on مع condition: service_healthy.

ولتطبيق Spring نفسه، يوفّر Actuator نقطة /actuator/health نستعملها لفحص صحّة التطبيق.

Spring profile للحاويات

نفعّل profile خاصًّا بالبيئة الحاوية عبر SPRING_PROFILES_ACTIVE=docker، فتُطبَّق إعدادات application-docker.properties عند التشغيل في الحاوية.

تشبيه من الواقع

✅ لا تبدأ قبل أن يجهز شريكك

التطبيق والقاعدة كزميلَي عمل: لا فائدة أن يبدأ التطبيق ويطلب البيانات قبل أن تفتح القاعدة أبوابها. الـ health check هو «إشارة الجاهزية» التي ينتظرها التطبيق.

المعمل التطبيقي

🧪 معمل 9: حزمة Spring Boot كاملة

هدف المعمل: تطبيق Spring Boot يعمل مع PostgreSQL ببيانات دائمة وانتظار صحيح.

  1. ابنِ jar التطبيق.
  2. أضف Dockerfile وcompose.yaml كما في المثال.
  3. فعّل Actuator (dependency spring-boot-starter-actuator) لنقطة الصحّة.
  4. شغّل: docker compose up -d --build.
  5. تحقّق من /actuator/health، ثم جرّب نقطة تنشئ بيانات.
  6. نفّذ down ثم up -d وتأكّد أن البيانات بقيت.

المخرجات: حزمة Spring Boot + PostgreSQL تعمل بأمر واحد — تطبيقك الآن كامل داخل حاويات. 🎉

أخطاء شائعة

⚠️ استخدام localhost في رابط القاعدة

داخل الحاوية localhost يعني التطبيق نفسه. استخدم اسم الخدمة: jdbc:postgresql://db:5432/tasks.

⚠️ بدء التطبيق قبل جاهزية القاعدة

depends_on وحده لا يكفي. أضف health check للقاعدة مع condition: service_healthy.

⚠️ نسيان volume القاعدة

بلا volume تضيع بيانات القاعدة عند down. اربط tasks-db بمجلد بياناتها.

❗ لا تضع الأسرار في الـ Image

كلمات المرور تُمرّر وقت التشغيل عبر البيئة أو .env، لا تُبنى داخل الـ Image.

أفضل الممارسات

⚙️ الإعدادات من البيئة

مرّر رابط القاعدة وبياناتها عبر متغيّرات البيئة (مبدأ 12-factor).

❤️ Actuator للصحّة

استخدم /actuator/health لفحص صحّة التطبيق داخل Compose أو المنسّق.

⏳ انتظر الجاهزية

health check + service_healthy بدل الاعتماد على ترتيب البدء فقط.

🧬 profile للحاوية

SPRING_PROFILES_ACTIVE=docker لفصل إعدادات الحاوية.

الخلاصة

أهم الأفكار

  • حاويّة Spring Boot = Image فيها JRE + نسخ الـ jar + تشغيله.
  • اضبط القاعدة عبر SPRING_DATASOURCE_*، وصِل بالاسم db.
  • health check + service_healthy يضمنان بدء التطبيق بعد جاهزية القاعدة.
  • volume للقاعدة يحفظ البيانات، و Actuator يفحص الصحّة.

عناصر مهمة

  • SPRING_DATASOURCE_URL / SPRING_PROFILES_ACTIVE
  • healthcheck / condition: service_healthy

أخطاء تجنّبها

  • localhost في رابط القاعدة.
  • بدء التطبيق قبل جاهزية القاعدة.
