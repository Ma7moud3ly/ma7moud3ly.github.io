Chapter 9: Spring Boot with PostgreSQL

Now we bring everything we've learned together on a real app: a Spring Boot service with a PostgreSQL database, in containers, with persistent data and a proper wait for the database to be ready.

Here you'll see why every earlier chapter mattered: an Image for the app, a volume for the data, a network for communication by name, and Compose to tie them together.

Containerizing a Spring Boot app

Spring Boot builds a single jar that contains everything (a fat jar). Its container is therefore simple: a JRE image, copy the jar, and run it. No fundamental difference from any Java app.

Connecting Spring to the database via the environment

We don't hard-code the database URL in the code. Spring Boot reads its settings from environment variables, so we pass them to the container:

  • SPRING_DATASOURCE_URL — the database's JDBC URL.
  • SPRING_DATASOURCE_USERNAME — the username.
  • SPRING_DATASOURCE_PASSWORD — the password.

✅ Reach by name

In the database URL we use the service name as the hostname: jdbc:postgresql://db:5432/tasks. The word db is the database service's name in Compose, not localhost.

Health check and waiting for readiness

We saw that depends_on guarantees the database started, not that it's ready. The solution is a health check on the database, then making the app wait until it becomes "healthy":

  • The database: a pg_isready check that repeats until it succeeds.
  • The app: depends_on with condition: service_healthy.

And for the Spring app itself, Actuator provides an /actuator/health endpoint we use to check the app's health.

A Spring profile for containers

We activate a container-specific profile with SPRING_PROFILES_ACTIVE=docker, so the settings in application-docker.properties apply when running in the container.

Real-world analogy

✅ Don't start before your partner is ready

The app and the database are like two coworkers: there's no point in the app starting and asking for data before the database opens its doors. The health check is the "ready signal" the app waits for.

  1. Build the app's jar.
  2. Add a Dockerfile and compose.yaml as in the example.

Common mistakes

⚠️ Using localhost in the database URL

Inside the container, localhost means the app itself. Use the service name: jdbc:postgresql://db:5432/tasks.

⚠️ Starting the app before the database is ready

depends_on alone isn't enough. Add a health check on the database with condition: service_healthy.

⚠️ Forgetting the database volume

Without a volume, the database's data is lost on down. Mount tasks-db at its data directory.

❗ Don't put secrets in the Image

Passwords are passed at run time via the environment or .env, never baked into the Image.

Best practices

⚙️ Config from the environment

Pass the database URL and credentials via environment variables (the 12-factor principle).

❤️ Actuator for health

Use /actuator/health to check the app's health inside Compose or an orchestrator.

⏳ Wait for readiness

A health check + service_healthy instead of relying on start order alone.

🧬 A profile for the container

SPRING_PROFILES_ACTIVE=docker to separate container settings.

Summary

Key ideas

  • A Spring Boot container = a JRE image + copying the jar + running it.
  • Configure the database via SPRING_DATASOURCE_*, and connect by the name db.
  • A health check + service_healthy ensures the app starts after the database is ready.
  • A volume for the database persists the data, and Actuator checks health.

Important items

  • SPRING_DATASOURCE_URL / SPRING_PROFILES_ACTIVE
  • healthcheck / condition: service_healthy

Mistakes to avoid

  • localhost in the database URL.
  • Starting the app before the database is ready.
