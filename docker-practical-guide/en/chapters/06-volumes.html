Chapter 6: Volumes

In the Containers chapter we hit a troubling problem: when you remove a container, its data disappears. That's fine for the app itself (it's ephemeral), but disastrous for a database.

The solution is storage outside the container. In this chapter we learn Docker's two storage types — Named Volumes and Bind Mounts — and when to use each.

Why does data disappear?

Every container writes its changes to its own thin writable layer on top of the read-only image layers. That layer is tied to the container's life: remove the container, and the layer — and all its data — is gone.

So we need storage that is independent of the container's lifecycle. Docker offers two main kinds:

Named Volumes — managed by Docker

A storage area Docker manages in its own region on the host. You give it a name, attach it to any container, and it stays even if the container is removed. This is the best fit for persistent data such as databases.

Bind Mounts — mapping a host path

This maps a specific folder or file from the host filesystem directly into the container. Any change on either side is reflected on the other immediately, which makes it ideal for development (live code or config).

💡 A brief third type

There's also tmpfs, which stores in memory (RAM) only and vanishes when the container stops — useful for sensitive temporary data, and rarely used.

Real-world analogy

✅ An external drive and a shared folder

A Named Volume is like an external drive Docker manages: you detach it from one container and attach it to another, and the data stays safe no matter what happens to the container. A Bind Mount is like a "shared folder" between your machine and the container: what you edit on your machine, the container sees instantly.

Common mistakes

⚠️ Expecting data to persist without a volume

Without a volume, everything the container wrote is deleted with it. Mount a volume for any data that must survive.

⚠️ A Bind Mount for database data

On Windows/macOS it can cause performance and permission issues. For persistent data prefer a Named Volume, and keep Bind Mounts for development.

⚠️ Anonymous volumes piling up

Some Images create anonymous volumes automatically. Clean them periodically with docker volume prune.

❗ Removing a container ≠ removing the volume

docker rm does not remove the Named Volume (by design, to protect your data). To remove it explicitly, use docker volume rm.

Best practices

🗄️ Named Volume for persistent data

Databases and uploaded files → always a Named Volume.

💻 Bind Mount for development

To mount live code or config files during local development.

🏷️ Name volumes clearly

tasks-db is clearer than an anonymous volume when maintaining or backing up.

🔒 :ro for read-only

Mount as read-only whatever the container doesn't need to write to.

Summary

Key ideas

  • Container data is ephemeral; persistent storage lives in an independent volume.
  • Named Volume (Docker-managed) for persistent data; Bind Mount (host path) for development.
  • Removing a container doesn't remove the Named Volume.
  • PostgreSQL persists its data by mounting a volume at /var/lib/postgresql/data.

Important commands

  • docker volume create / ls / inspect / rm / prune
  • -v name:/path and -v /host:/path:ro

Mistakes to avoid

  • Expecting data to persist without a volume.
  • A Bind Mount for database data in production.
