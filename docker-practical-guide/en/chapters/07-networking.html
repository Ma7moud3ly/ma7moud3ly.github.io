Chapter 7: Networking

A container rarely works alone. The app needs to talk to a database, and the outside world needs to reach the app. This chapter explains how containers communicate: with each other over the network, and with the outside via port mapping.

The most important idea here — and the most often overlooked — is that containers on a user-defined network find each other by name automatically. That's what will connect our app to its database later.

Network drivers

Docker provides several network "drivers," three of them most important:

TypeDescription
bridgeThe default; a private isolated network on the host (most used)
hostShares the host's network stack directly, no isolation (Linux)
noneNo network at all (full isolation)

The default network vs a user-defined one

Every container joins a default bridge network by default. But this default network has an important limitation: its containers don't recognize each other by name — only by IP addresses, which are changeable and impractical.

❗ The golden rule

Always create a user-defined bridge for your app. Only there does internal DNS work, so each container reaches another by its name as a hostname. This is what lets your app reach the database via db instead of an IP address.

Port mapping

The network connects containers to each other, but to reach one from outside Docker (like your browser) we need to publish a port with -p:

Remember the difference from the Dockerfile chapter: EXPOSE is documentation only, while -p is what actually publishes the port to the host.

host and none networks

The host network makes the container share the host's network directly (no need for -p), but with no isolation, and it works fully only on Linux. none isolates the container from any network entirely.

Real-world analogy

✅ An internal phone system

A user-defined network is like a company's internal phone system: each employee (container) has a name and calls colleagues by name through an internal directory (DNS). Port mapping (-p) is like the receptionist who forwards an outside call to a specific internal extension.

⚠️ Don't use localhost between containers

Inside a container, localhost means the container itself, not the host or another container. To reach another container, use its name on the shared network.

Common mistakes

⚠️ Expecting name resolution on the default network

Internal DNS only works on a user-defined network. Create one with docker network create and attach your containers to it.

⚠️ Reversing the -p order

The syntax is host:container. Writing -p 80:8080 instead of -p 8080:80 forwards the request to the wrong port.

⚠️ Forgetting to put containers on the same network

Two containers on different networks can't see each other. They must share the same network to communicate.

⚠️ Publishing the database port needlessly

If only the app needs the database, there's no need to publish 5432 to the host; it's enough that the database is on the same network.

Best practices

🔗 A user-defined network per app

Group one app's containers on its own network to isolate them and enable DNS.

🏷️ Connect by name, not IP

IP addresses change; container names are stable and clear.

🔒 Publish the fewest ports

Publish only what the outside world needs, and keep the rest internal.

Summary

Key ideas

  • Create a user-defined bridge for any multi-container app.
  • On a user-defined network, containers recognize each other by name via internal DNS.
  • -p host:container publishes the port to the outside; EXPOSE is documentation only.
  • localhost inside a container means the container itself, not another container.

Important commands

  • docker network create / ls / inspect / connect
  • --network <name> and -p host:container

Mistakes to avoid

  • Relying on the default network for name resolution.
  • Using localhost between containers.
