Why Docker? The "works on my machine" problem

Imagine you just finished building your app on your machine. It runs great. You send it to a colleague or to the server, and it breaks immediately. Why?

Because no app runs in a vacuum — it depends on a whole environment around it:

  • A specific runtime version and libraries.
  • Environment variables and settings.
  • External services such as a database of a certain version.
  • Ports and operating-system libraries.

Any small difference in this environment between your machine and the server can break the app. That's the famous "works on my machine" problem.

A concrete example: a Java app depends on a JRE for Java 21 on your machine, while the server only has Java 17 — so it fails to run.

What does Docker solve?

Docker's idea is simple. Instead of moving the app alone, we package it with its entire environment into a single unit called an Image.

This unit runs the same way on any machine that has Docker: yours, your colleague's, or the server. The differences disappear, and so does the problem.

✅ The core idea

Docker doesn't make your app faster; it makes it run the same everywhere. The real value is consistency between development and production.

Virtual Machines

Before containers, isolation was usually done with a virtual machine. A VM emulates a whole machine: each app gets its own guest OS running on top of a layer called a Hypervisor.

This gives strong isolation, but at a cost:

  • Each VM carries a full OS — gigabytes in size.
  • Booting takes minutes.
  • High memory and CPU usage, because every guest OS runs in full.

Containers

A container solves the same isolation problem far more lightly. Instead of emulating a whole machine, all containers share the host operating system kernel and run as isolated processes on top of it.

The result:

  • Size in megabytes, not gigabytes.
  • Boot in seconds or less.
  • Far lower usage — you can run dozens of containers on one machine.

❗ Very important

A container is not a small virtual machine — it's an isolated process. It has no full OS, only the app's files and environment, and it borrows the kernel from the host.

Images and Containers

These two terms are the heart of Docker, and mixing them up is common. The difference is simple:

  • Image: a read-only template that contains your app and everything it needs to run. It doesn't run by itself — it's just a "blueprint."
  • Container: a live, runnable instance of the Image. From a single Image you can run any number of containers.

✅ In Java terms

If you know Java, the analogy is direct: the Image is like a Class, and the Container is like an Object (an instance of the class). Just as you create many objects from one class, you run many containers from one Image.

Real-world analogy

Docker is named after dock workers who ship containers, and the analogy is intentional:

✅ The shipping container

Before standard shipping containers, every kind of cargo was shipped its own way — chaos. Then came the standardized container: one fixed-size box that any crane can lift and any ship or truck can carry, regardless of what's inside.

A Docker container does the same for software: it wraps your app in a standard "box" that runs on any Docker-capable infrastructure, without that infrastructure caring what's inside.

Common mistakes

⚠️ Treating a container as a small VM

A common mistake. A container is an isolated process that shares the host kernel, not a full OS. That's why it's lighter and faster — and also why it can't run a kernel entirely different from the host's.

⚠️ Confusing Image and Container

The Image is a static template; the Container is a live run of it. Changing a container doesn't change the image it was built from.

⚠️ Thinking Docker replaces the runtime

Docker doesn't replace your app's runtime — it bundles it. A Java app still needs a JRE, but now the JRE lives inside the image at a version we know and control.

Best practices

📦 One process per container

Make each container responsible for one thing: the Spring Boot service in one, the database in another.

🧊 The image is an immutable artifact

Treat the image as an immutable artifact: built once, run unchanged across all environments.

♻️ Containers are disposable

Treat a container as ephemeral: you can delete and recreate it at any moment without fear.

Summary

Key ideas

  • Docker solves "works on my machine" by packaging the app with its environment.
  • A container is an isolated process sharing the host kernel — lighter and faster than a VM.
  • The Image is a static template; the Container is a live run of it (Class vs Object).
  • Docker's architecture = Client + Daemon + Registry.

Terms to remember

  • Image / Container / Registry
  • Docker Client / Docker Daemon

Mistakes to avoid

  • Treating a container as a small VM.
  • Confusing image and container.
  • Thinking Docker replaces the JVM.
