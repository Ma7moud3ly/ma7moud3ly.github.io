الفصل 8: Docker Compose

في معمل الشبكات كتبنا أوامر docker run طويلة لتشغيل التطبيق والقاعدة معًا. تخيّل تكرار ذلك كل مرة، وتذكّر الشبكة والـ volume والترتيب. مُتعب.

Docker Compose يحلّ هذا. نصف التطبيق كله في ملف واحد اسمه compose.yaml، ونشغّله بأمر واحد.

⏱️ زمن القراءة: — 📊 المستوى: متوسّط 🧪 معمل تطبيقي واحد

أهداف التعلّم

بنهاية هذا الفصل ستعرف كيف:

  • تشرح ما يحلّه Docker Compose.
  • تكتب ملف compose.yaml بخدمات وشبكات و volumes.
  • تشغّل التطبيق كله وتوقفه بأمر واحد.
  • تمرّر متغيّرات البيئة عبر Compose وملف .env.
  • تضبط ترتيب الإقلاع بـ depends_on.

المتطلبات المسبقة

  • إنهاء الفصل 6 (Volumes) والفصل 7 (Networking).
  • وجود Image لتطبيقك (my-app:1.0 من معمل الفصل 5).

ما هو Docker Compose؟

أداة تصف تطبيقًا متعدّد الحاويات في ملف compose.yaml، ثم تديره بأمر واحد. بدل عدة أوامر docker run، كل شيء في ملف واحد واضح وقابل للحفظ في Git.

بنية compose.yaml

الملف مقسّم إلى أقسام بسيطة:

  • services: كل خدمة حاوية (مثل app وdb).
  • volumes: الـ Named Volumes الدائمة.
  • networks: الشبكات (اختياري — يُنشئ Compose واحدة تلقائيًّا).

وداخل كل خدمة نحدّد image أو build، والمنافذ، والبيئة، والـ volumes، والاعتماد على خدمات أخرى.

✅ شبكة تلقائية و DNS بالاسم

ينشئ Compose شبكة معرّفة لتطبيقك تلقائيًّا، ويضع كل الخدمات عليها. لذلك تصل كل خدمة إلى الأخرى باسمها مباشرةً — يصل app إلى القاعدة عبر db، تمامًا كما تعلّمنا في فصل الشبكات.

متغيّرات البيئة وملف .env

نمرّر الإعدادات عبر environment داخل الخدمة. ولإبقاء القيم خارج الملف، نضعها في ملف .env ويقرأها Compose تلقائيًّا.

ترتيب الإقلاع: depends_on

يحدّد depends_on أن خدمة تبدأ قبل أخرى (مثل: القاعدة قبل التطبيق).

⚠️ يبدأ ≠ جاهز

depends_on يضمن أن القاعدة بدأت، لا أنها جاهزة لقبول الاتصالات. حلّ الانتظار الحقيقي عبر health check — نراه في الفصل التالي.

تشبيه من الواقع

المعمل التطبيقي

🧪 معمل 8: حوّل الأوامر الطويلة إلى Compose

في معمل الفصل 7 شغّلنا التطبيق والقاعدة بأمرين طويلين. لنستبدلهما بملف واحد.

  1. في مجلد المشروع، أنشئ compose.yaml كما في المثال أعلاه.
  2. شغّل الحزمة: docker compose up -d.
  3. تأكّد من الخدمتين: docker compose ps.
  4. افتح http://localhost:8080 وجرّب التطبيق.
  5. أوقف الحزمة: docker compose down، ثم أعد up -d ولاحظ بقاء البيانات (الـ volume).

المخرجات: حزمة تعمل بأمر واحد. في الفصل التالي نبنيها بشكل صحيح لتطبيق Spring Boot مع health check.

أخطاء شائعة

⚠️ مسافات YAML خاطئة

YAML حسّاس للمسافات (indentation). استخدم مسافات لا Tabs، وحاذِ الأقسام بدقّة.

⚠️ نسيان الـ volume للقاعدة

بلا volumes في القاعدة، تضيع بياناتها عند down. اربط دائمًا volume لبيانات القاعدة.

⚠️ الاعتماد على depends_on للجاهزية

يضبط ترتيب البدء فقط، لا الجاهزية. للانتظار الفعلي استخدم health check (الفصل التالي).

⚠️ استخدام docker-compose القديم

الأمر الحديث هو docker compose (بمسافة). صيغة docker-compose بشرطة قديمة.

أفضل الممارسات

🗂️ خدمة لكل مسؤولية

افصل التطبيق عن القاعدة عن الكاش، كل واحد خدمة مستقلّة.

🔑 الإعدادات في .env

أبقِ القيم والأسرار خارج compose.yaml ولا ترفعها إلى Git.

📌 ثبّت إصدارات الـ Images

postgres:16 لا postgres:latest.

💾 volume لكل بيانات دائمة

قواعد البيانات والملفات المرفوعة → Named Volume.

الخلاصة

أهم الأفكار

  • Compose يصف تطبيقًا متعدّد الحاويات في ملف واحد ويشغّله بأمر واحد.
  • ينشئ شبكة تلقائيًّا، فتتعارف الخدمات بالاسم.
  • depends_on يضبط ترتيب البدء لا الجاهزية.
  • الـ Named Volumes تبقى بعد down (إلا مع -v).

أوامر مهمة

  • docker compose up -d / ps / logs
  • docker compose down / down -v

أخطاء تجنّبها

  • مسافات YAML خاطئة.
  • توقّع أن depends_on ينتظر الجاهزية.
